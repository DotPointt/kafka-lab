# 1. Kafka за 10 минут

> **Kafka — это распределённый, реплицированный, append-only лог.** Producer-ы дописывают события в конец лога, consumer-ы читают его с любого места и сами помнят, где остановились. Сообщения не удаляются после прочтения — они живут, пока не истечёт retention.

Если запомнить только одну фразу — запомни эту. Почти всё остальное в Kafka из неё следует.

## Зачем она нужна

- **Развязать сервисы.** Producer не знает, кто и когда прочитает событие. Добавить нового потребителя — значит просто подписать новую consumer group.
- **Буфер между быстрыми и медленными.** Пики нагрузки складываются в лог, консюмеры разбирают их в своём темпе (растёт lag, но ничего не теряется).
- **Много читателей одного потока.** Один топик `orders` читают и обработка заказов, и аналитика, и аудит — независимо.
- **Перечитать историю.** Нашли баг в обработке — откатили offset группы и пересчитали. Подняли новый сервис — накормили его историей.
- **Высокая пропускная способность.** Сотни тысяч и миллионы сообщений в секунду на кластер за счёт batching, последовательной записи и партиционирования.

## Ментальная модель

```text
                         топик "orders" = 3 партиции (у каждой свой лог и свои offset-ы)
                       ┌──────────────────────────────────────────┐
  Producer ─key=c7──►  │ P0: [0][1][2][3][4][5][6] ← конец лога   │ ──► group "order-processing": P0 → offset 5
          ─key=c2──►   │ P1: [0][1][2][3]                         │ ──► group "analytics":        P0 → offset 2
          ─key=c9──►   │ P2: [0][1][2][3][4]                      │       (у каждой группы свои offset-ы)
                       └──────────────────────────────────────────┘
          каждая партиция хранится в 3 копиях (RF=3) на разных брокерах: 1 лидер + 2 follower-а
```

- **Топик** — именованный поток событий (`orders`, `payments`).
- **Партиция** — кусок топика, отдельный упорядоченный лог. Партиции — единица параллелизма: их читают разные консюмеры одновременно.
- **Offset** — номер сообщения внутри партиции. Пара (партиция, offset) однозначно указывает на сообщение.
- **Ключ** определяет партицию: `murmur2(key) % число_партиций`. Сообщения с одним ключом всегда в одной партиции → по ним сохраняется порядок.
- **Брокер** — сервер Kafka, хранит реплики партиций. Несколько брокеров = кластер.
- **Реплики**: у каждой партиции есть **лидер** (принимает запись и обслуживает чтение) и **follower-ы** (копируют лог лидера). **ISR** — реплики, которые не отстают.
- **Контроллер** (KRaft) — «мозг» кластера: хранит метаданные, выбирает лидеров партиций, следит за живостью брокеров.
- **Consumer group** — несколько консюмеров с общим `group.id`. Партиции делятся между ними; каждая группа читает топик целиком и независимо от других групп.

## Словарь

| Термин | Что это | Где увидеть на стенде |
|---|---|---|
| Broker | Сервер Kafka, хранит реплики партиций | Карточки Broker 1/2/3 |
| Topic | Именованный поток сообщений | Строки orders, payments, clickstream… |
| Partition | Упорядоченный лог внутри топика | Чипы с номерами 0…5 |
| Replica / RF | Копия партиции / сколько копий | Один номер партиции встречается на нескольких брокерах |
| Leader | Реплика, через которую идёт запись | Залитый чип с жёлтой точкой |
| ISR | In-Sync Replicas — не отстающие реплики | Контурные чипы; пунктир = вне ISR |
| Offset | Номер сообщения в партиции | Таблица «Партиции и offset-ы» |
| High Watermark | До какого offset можно читать | Колонка «конец» |
| Consumer group | Группа консюмеров с общими offset-ами | Карточки order-processing, analytics |
| Coordinator | Брокер, управляющий группой | «коорд. b2» в карточке группы |
| Lag | Насколько группа отстала от конца лога | Большое число в карточке группы |
| Controller | Лидер кворума метаданных (KRaft) | ★ «активный контроллер» |

## Путь одного сообщения

1. Producer сериализует ключ и значение в байты.
2. **Partitioner** выбирает партицию: по ключу (murmur2) или, если ключа нет, «липко» — весь batch в одну партицию.
3. Сообщение ложится в **локальный буфер** producer-а, в batch нужной партиции. `Produce()` на этом заканчивается — он асинхронный.
4. Фоновый поток отправляет batch **лидеру партиции** (producer заранее знает из метаданных, какой брокер лидер).
5. Лидер дописывает batch в конец лога (в page cache ОС) и присваивает offset-ы.
6. Follower-ы забирают новые данные у лидера (fetch — как обычные консюмеры).
7. Когда запись есть у всех реплик ISR, лидер двигает **high watermark**. При `acks=all` только теперь producer получает подтверждение.
8. Consumer шлёт fetch-запрос лидеру «дай данные начиная с offset N» и получает batch-и (только до high watermark).
9. Обработав сообщения, consumer **коммитит offset** — записывает в служебный топик `__consumer_offsets` «группа G прочитала партицию P до offset N».

## Чем Kafka НЕ является

- **Не классическая очередь.** Нет ack/удаления отдельного сообщения, нет приоритетов, нет «отложенной доставки» из коробки. Consumer подтверждает не сообщение, а *позицию в логе*.
- **Не база данных для запросов.** Найти сообщение по полю нельзя — только читать лог (или строить поверх Kafka Streams/ksqlDB/внешнюю БД).
- **Не глобально упорядоченная.** Порядок есть только внутри партиции.
- **Не exactly-once «магически».** Дубли и потери — вопрос настроек producer-а, консюмера и идемпотентности обработки (см. [гарантии доставки](06-guarantees.md)).

## Что изменилось в Kafka 4.x

- **ZooKeeper удалён полностью** — только KRaft (контроллеры на Raft). Стенд работает именно так.
- **KIP-848** — новый протокол consumer group (`group.protocol=consumer`): ребаланс считает брокер, без stop-the-world.
- **Share groups (KIP-932, «очереди в Kafka»)** — консюмеры делят сообщения, а не партиции, с подтверждением каждого сообщения. В 4.0 early access, в 4.1 preview.
- По умолчанию у Java-producer `linger.ms=5` (раньше 0), `acks=all` и идемпотентность включены с 3.0.
