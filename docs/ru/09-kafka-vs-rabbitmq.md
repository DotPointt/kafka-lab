# 9. Kafka vs RabbitMQ

Оба — «брокеры сообщений», но устроены противоположно. Kafka — **лог**, RabbitMQ — **очередь с маршрутизацией**.

## Главное различие

```text
RabbitMQ:  producer ─► exchange ─(routing key, bindings)─► queue ─► consumer ─ ack ─► сообщение удалено
Kafka:     producer ─► topic/partition (лог) ◄─ consumer читает с offset N и сам помнит позицию; сообщение остаётся
```

- В RabbitMQ брокер **знает о каждом сообщении**: кому доставлено, подтверждено ли, сколько раз переотправлено. «Умный брокер — простой консюмер».
- В Kafka брокер просто хранит лог, а **позицию ведёт консюмер** (группа). «Простой брокер — умный консюмер».

## Сравнение

| | Kafka | RabbitMQ |
|---|---|---|
| Модель | Реплицированный лог, pub/sub через consumer groups | Очереди + exchanges (direct, topic, fanout, headers) |
| После чтения | Остаётся до retention | Удаляется после ack |
| Перечитать историю | Да (seek, reset offsets) | Нет (кроме RabbitMQ Streams) |
| Подтверждение | Позиция (offset) на партицию | Каждое сообщение (ack/nack/reject) |
| Порядок | В пределах партиции | В пределах очереди (нарушается при requeue и нескольких консюмерах) |
| Масштабирование чтения | Партиции (≤ 1 консюмер группы на партицию) | Конкурирующие консюмеры одной очереди |
| Маршрутизация | Только топик + ключ → партиция | Гибкая: routing keys, шаблоны, заголовки |
| Приоритеты, TTL, отложенная доставка | Нет (паттерны поверх) | Есть (priority queues, TTL, delayed plugin) |
| DLQ | Паттерн приложения | Встроено (dead letter exchange) |
| Пропускная способность | Очень высокая (миллионы msg/s на кластер) | Высокая, но ниже; лучше для малых объёмов с низкой задержкой |
| Хранение | Долгое, дисковое, дешёвое | Короткое: очередь должна быть пустой |
| Протокол | Собственный бинарный (TCP) | AMQP 0-9-1, AMQP 1.0, MQTT, STOMP |
| Репликация | ISR, KRaft | Quorum queues (Raft), Streams |
| Экосистема | Kafka Connect, Streams, ksqlDB, Schema Registry, CDC | Плагины, shovel, federation |

## Соответствие понятий

| RabbitMQ | Kafka |
|---|---|
| Queue | Партиция + consumer group (позиция группы) |
| Exchange + binding | Нет; producer сам выбирает топик (маршрутизацию делают сервисы или Kafka Streams) |
| Competing consumers на одной очереди | Консюмеры одной группы на партициях топика |
| Fanout в несколько очередей | Несколько consumer groups на одном топике |
| ack / nack / requeue | commit offset (нет отдельного nack — только ретрай в коде или DLQ-топик) |
| Dead letter exchange | DLQ-топик (паттерн) |
| prefetch | max.poll.records / fetch.max.bytes |

## Когда что выбирать

**Kafka**, если:
- нужен **поток событий**, который читают много независимых потребителей (event-driven, event sourcing, CDC);
- нужно **хранить и перечитывать** историю, строить аналитику и стриминг;
- большие объёмы и высокая пропускная способность;
- важен порядок событий по ключу (по сущности).

**RabbitMQ**, если:
- нужна **очередь задач** (task queue) с конкурирующими воркерами и поштучным ack;
- сложная **маршрутизация** по ключам/заголовкам, request-reply (RPC);
- приоритеты, TTL, отложенная доставка, встроенная DLX;
- небольшие объёмы, важна минимальная задержка и простота.

> Новое в обоих мирах: в RabbitMQ есть **Streams** (лог «как в Kafka»), а в Kafka — **share groups** (KIP-932): консюмеры делят сообщения, а не партиции, с поштучным подтверждением — «очереди в Kafka».
