# 5. Хранение: сегменты, retention, compaction

## Как партиция лежит на диске

```text
/var/lib/kafka/data/orders-3/
   00000000000000000000.log        ← сегмент: batch-и сообщений подряд
   00000000000000000000.index      ← разреженный индекс offset → позиция в .log
   00000000000000000000.timeindex  ← время → offset
   00000000000000052341.log        ← активный сегмент (имя = первый offset в нём)
   00000000000000052341.index
   leader-epoch-checkpoint         ← история эпох лидеров (для обрезки лога)
```

- Пишется только **активный сегмент**, остальные неизменяемы.
- Новый сегмент начинается по размеру (`segment.bytes`, 1 GB) или времени (`segment.ms`, 7 дней).
- Удаляются и компактятся **целые закрытые сегменты** — retention «квантуется» по сегментам.
- Посмотреть содержимое: `kafka-dump-log.sh --files .../00000000000000000000.log --print-data-log`.

## Почему это быстро

- **Последовательная запись** в конец файла — диски (и SSD, и HDD) это любят.
- **Page cache ОС** вместо собственного кэша: свежие данные читаются из памяти. Kafka не делает fsync на каждое сообщение — надёжность обеспечивает **репликация**, а не диск одного узла.
- **Zero-copy** (`sendfile`): данные идут из page cache в сокет без копирования в user space (без TLS).
- **Batching и сжатие** на всём пути: producer → диск → consumer видят одни и те же batch-и.

## Retention (cleanup.policy=delete)

| Настройка | По умолчанию | Смысл |
|---|---|---|
| `retention.ms` | 7 дней | Удалять сегменты старше |
| `retention.bytes` | −1 (без лимита) | Лимит размера **на партицию** |
| `segment.bytes` / `segment.ms` | 1 GB / 7 дней | Когда закрывать сегмент |
| `log.retention.check.interval.ms` | 5 мин | Как часто проверять |

Consumer, чей offset «уехал» за удалённые сегменты, получит `OFFSET_OUT_OF_RANGE` и прыгнет по `auto.offset.reset`.

На стенде у `clickstream` retention 10 минут и 100 MB на партицию — нагрузочный тест не съест диск.

## Log compaction (cleanup.policy=compact)

Топик превращается в «таблицу»: для каждого ключа хранится **последнее значение**.

```text
 до компакции:   k1=a  k2=b  k1=c  k3=d  k2=null  k1=e
 после:                                   k3=d  k2=null  k1=e      (k2=null — tombstone, удалится позже)
```

- Компактятся только закрытые сегменты («грязная» часть лога). Активный — никогда.
- Отдельные потоки **log cleaner** запускаются, когда доля грязных данных ≥ `min.cleanable.dirty.ratio` (0.5).
- **Tombstone** — сообщение с `value = null`: удаляет ключ. Сам tombstone живёт ещё `delete.retention.ms` (1 день), чтобы консюмеры успели его увидеть.
- `min.compaction.lag.ms` — не компактить слишком свежие сообщения.
- Offset-ы **не перенумеровываются** — после компакции в них «дырки».
- Можно `cleanup.policy=compact,delete` — последнее значение по ключу, но не дольше retention.

Где применяется: `__consumer_offsets`, changelog-топики Kafka Streams (KTable), справочники, текущее состояние сущностей, CDC (Debezium).

На стенде: `customer-profiles` — order-service пишет туда профиль клиента после каждого заказа. Ключей 50, сообщений тысячи; после компакции останется по одному на ключ. Кнопка «🪦 tombstone» удаляет ключ.

## Размер сообщений

- `message.max.bytes` (брокер, ≈1 MB) / `max.message.bytes` (топик), `max.request.size` (producer), `fetch.max.bytes` / `max.partition.fetch.bytes` (consumer) — должны быть согласованы.
- Большие объекты (файлы, картинки) в Kafka не кладут: хранят в объектном хранилище, а в событии — ссылку (claim check pattern).

## Tiered storage (KIP-405)

Старые сегменты можно выгружать в объектное хранилище (S3 и т. п.), оставляя на брокерах только «горячий» хвост. Удобно для длинного retention без огромных дисков.
