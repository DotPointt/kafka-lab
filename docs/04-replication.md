# 4. Репликация, ISR и KRaft

## Лидер и follower-ы

У каждой партиции `replication.factor` реплик на разных брокерах. Одна — **лидер**: принимает запись, обслуживает чтение (по умолчанию). Остальные — **follower-ы**: они сами забирают данные у лидера Fetch-запросами (pull-модель, как обычные консюмеры).

```text
            LEO = log end offset (следующий offset для записи у реплики)
            HW  = high watermark  (до него запись есть у всех ISR → её можно отдавать консюмерам)

 лидер     [0][1][2][3][4][5][6][7]        LEO=8
 follower1 [0][1][2][3][4][5][6]           LEO=7
 follower2 [0][1][2][3][4][5]              LEO=6     →  HW = min(LEO по ISR) = 6
                         ▲
 консюмеры видят offset-ы 0…5; 6 и 7 ещё «неподтверждённые»
```

- Консюмер **никогда не видит данные выше HW** — поэтому он не прочитает запись, которая может исчезнуть при смене лидера.
- `acks=all` подтверждает запись, когда HW дошёл до неё.

## ISR — In-Sync Replicas

- Реплика в ISR, если дочитывала лог лидера в последние `replica.lag.time.max.ms` (30 c по умолчанию, на стенде 10 c).
- Отстала (брокер упал, завис, сеть медленная) → лидер **сжимает ISR** (shrink) через контроллер.
- Догнала → **расширяет ISR** (expand).
- **Under-replicated partition (URP)**: ISR < RF. Работает, но запас прочности снижен. Главный алерт эксплуатации.

### min.insync.replicas

Минимальный размер ISR для записи с `acks=all`. Классика — **RF=3, min.insync.replicas=2**:

| Живых реплик в ISR | acks=all | acks=1 |
|---|---|---|
| 3 | ✅ | ✅ |
| 2 | ✅ (терпим потерю одного брокера) | ✅ |
| 1 | ❌ `NOT_ENOUGH_REPLICAS` | ✅ (но риск потери) |
| 0 (нет лидера) | ❌ offline | ❌ offline |

## Выборы лидера

1. Брокер-лидер умер / зафенсен / остановлен.
2. Контроллер выбирает нового лидера **из ISR** (обычно первого живого в списке replicas).
3. Новый лидер получает новый **leader epoch**; метаданные рассылаются брокерам.
4. Клиенты получают `NOT_LEADER_OR_FOLLOWER`, обновляют метаданные и переключаются. Producer ретраит, консюмер продолжает со своего offset-а.

**Controlled shutdown** (SIGTERM, `docker stop`): брокер заранее просит контроллер перенести с него лидерство — клиенты почти не замечают. **Крэш** (SIGKILL): кластер ждёт, пока контроллер не заметит пропажу heartbeat-ов (`broker.session.timeout.ms`, 9 c).

**Preferred leader** — первая реплика в списке replicas. После возвращения брокера лидерство возвращается к нему не сразу: раз в `leader.imbalance.check.interval.seconds` (300 c, на стенде 30 c) или по команде `kafka-leader-election.sh --election-type PREFERRED`.

### Unclean leader election

Если ISR пуст (все синхронные реплики мертвы), можно выбрать лидером отставшую реплику — партиция оживёт, но подтверждённые данные пропадут. `unclean.leader.election.enable=false` (по умолчанию) — Kafka выбирает **недоступность**, а не потерю.

### Leader epoch и обрезка лога

Каждая смена лидера увеличивает epoch. Вернувшаяся реплика спрашивает у нового лидера: «до какого offset совпадают наши логи в моём последнем epoch?» (`OffsetsForLeaderEpoch`, KIP-101) и **обрезает** расхождение. Если старый лидер успел подтвердить что-то с `acks=1`, эти записи исчезнут — сценарий «Зомби-лидер» показывает это вживую.

### ELR (KIP-966, Kafka 4.x)

**Eligible Leader Replicas** — реплики, выкинутые из ISR потому, что ISR опустился ниже `min.insync.replicas`, но гарантированно содержащие все данные до HW. Их можно безопасно выбрать лидером, когда ISR пуст. Видно в `kafka-topics.sh --describe` (поля `Elr`, `LastKnownElr`).

## KRaft: контроллеры вместо ZooKeeper

С Kafka 4.0 ZooKeeper удалён. Метаданные кластера — тоже **лог**: топик `__cluster_metadata`, который реплицируют **контроллеры** по протоколу Raft.

```text
   controller 1 (follower) ◄─┐
   controller 2 (ЛИДЕР)  ────┼── лог метаданных: «создан топик», «лидер orders-3 = 2», «ISR orders-1 = [1,3]», «брокер 2 fenced»…
   controller 3 (follower) ◄─┘
          ▲  heartbeat-ы, AlterPartition (изменения ISR)
          │
   брокеры: получают изменения метаданных и применяют их локально
```

- **Активный контроллер** (лидер Raft-кворума) принимает все решения. Остальные — горячий резерв.
- Кворуму нужно **большинство**: 3 контроллера переживают потерю 1, 5 — потерю 2. Потеряли большинство — метаданные замораживаются: нельзя выбрать лидеров, зафенсить брокер, создать топик.
- **Регистрация и фенсинг брокеров**: брокер шлёт контроллеру heartbeat (`broker.heartbeat.interval.ms`, 2 c). Нет heartbeat дольше `broker.session.timeout.ms` (9 c) → брокер **fenced**: исключён из метаданных, его реплики убираются из ISR, лидерство переезжает.
- Обычный клиент активный контроллер не видит (говорит только с брокерами). Посмотреть: `kafka-metadata-quorum.sh --bootstrap-server localhost:9092 describe --status` / `--replication` — так это делает control-center.
- **Combined mode** (`process.roles=broker,controller`) — как на стенде. В продакшене контроллеры обычно отдельные (`process.roles=controller`).

## Что будет, если… (RF=3, min.isr=2, 3 узла)

| Событие | Что видно | Запись acks=all | Чтение |
|---|---|---|---|
| Остановили 1 брокер (graceful) | Лидеры переехали заранее, URP > 0 | ✅ | ✅ |
| Убили 1 брокер (SIGKILL) | ~9 c недоступности его партиций, затем выборы | ✅ после выборов | ✅ после выборов |
| Пауза брокера 4 c | Скачок задержки | ✅ (медленнее) | ✅ |
| Пауза брокера 20 c | Фенсинг, выборы, после разморозки — догоняет | ✅ после выборов | ✅ |
| Убили 2 брокера | Потеря кворума KRaft, ISR=1 | ❌ | Частично |
| Изолировали активный контроллер | Новый лидер кворума за секунды, изолированный брокер фенсится | ✅ после выборов | ✅ |
| Брокер отрезан от кластера, клиенты его видят | «Зомби-лидер»: с acks=1 подтверждает, потом обрезает лог | ❌ на зомби, ✅ у нового лидера | ✅ |
| Задержка сети 300 мс у брокера | Растёт p99 acks=all (ждём его fetch) | ✅ медленнее | ✅ |

## Rack awareness и перераспределение

- `broker.rack` + rack-aware размещение реплик: копии партиции в разных зонах доступности.
- `client.rack` + `replica.selector.class` (KIP-392): консюмер читает с ближайшей реплики-follower-а, экономя межзонный трафик.
- `kafka-reassign-partitions.sh` — перенос реплик между брокерами (например, при добавлении узлов). Новый брокер сам ничего не получает — партиции нужно перераспределить.
